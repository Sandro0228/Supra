# Supra: wedding seating planner

Couples sign in, draw their hall, seat guests (each guest is an illustrated character), print PDFs and place cards, and share a "find my seat" guest page (link + QR). English and Georgian. Goal: turn it into a paid product (couples pay per event, banquet halls/planners pay monthly). See `docs/ROADMAP.md` for the staged plan and risk register (R1–R12).

## Stack
- Plain static site, **no build step, no package.json**. ES2020 in IIFEs, string-template rendering into the DOM and SVG.
- Supabase (Auth + Postgres, RLS, `security definer` functions). Loaded from the CDN: `@supabase/supabase-js@2.45.4` UMD.
- Hosted on Vercel; auto-deploys from `main`. `vercel.json` rewrites `/edit/:id` and `/e/:slug` to `app.html`.

## Files
- `index.html` + `dash.js`: landing page (signed out: hero with the hall, how it works, guests' phone, place cards, sign-in; text via `data-t` keys `lp*`, pictures `landing/{hall,phone,cards}-{en,ka}.webp` made by `python3 tools/landing_shots.py` from a demo wedding in the real app), sign-in/sign-up, and "Your events" (signed in: only this; one card per event with the palette cover, countdown, seating progress and guest-page status; the new-event panel opens on demand or on first run).
- `app.html` + `js/*.js`: planner (`/edit/<id>`), public guest page (`/e/<token>`) and RSVP page (`/r/<token>`). ES modules: `app.html` loads `js/main.js`, which imports the rest and calls `boot()`. `appState.MODE` is `'edit'`, `'guest'` or `'rsvp'`. State several files change lives in `appState` (`js/core.js`), e.g. `appState.S` (the plan), `appState.sel`, `appState.panel`. **Read `js/README.md` before adding files, imports or top-level code.**
- `i18n.js`: `SUPRA_I18N.en` / `.ka` (~490 keys). `t(key, vars)` and `tn(key, n)` (plural forms `_one`/`_other`; Georgian nouns stay singular).
- `assets.js` (3 KB) + `img/*.webp`: the drawings (character parts, tables, decorations) as separate files named by content hash, cached for a year (`vercel.json`). `assets.js` holds only sizes, skin colours and the file list; it is generated by `tools/split_assets.py` (never edit by hand). Pages load only what they draw with `loadImages(keys)` in `js/core.js` (planner and guest page: all; RSVP: the household's `lookImages`). Images are kept in memory as data URLs so PNG/PDF exports keep working.
- The room (`hall()` in `js/draw.js`) is drawn from above like the plan: parquet, walls, windows with daylight, trees, entrance. Only guests are drawn from the front. New drawings come from Gemini on a solid green/magenta background; the originals live in `new-art/` (not committed), get cut out to `img/<key>.webp` and registered with `python3 tools/split_assets.py --from-dir`.
- Planner motion (`renderPlan` in `js/actions.js` + CSS in `app.html`): only in answer to what the organiser does, and off under prefers-reduced-motion.
- `names.js`: guesses man/woman from Georgian/English first names, the family (surname) and grandparents (titles). `smartLook()` in `js/core.js` uses these plus the couple's "Typical guests" shades (`S.event.crowd`) for a new guest's first drawing; relatives look alike. Looks changed by hand carry `look.hand` and are never restyled.
- `brand.*`, `brand/`: logo and theme switch. `config.js`: public Supabase URL and publishable key (safe to commit).
- `supabase/*.sql`: migrations, run by hand in order (`schema.sql`, then `002`–`008`) in the Supabase SQL editor. Each file has rollback notes at the top.

## Data model
- One table `public.events`: `owner`, `name`, `type`, `event_date`, `slug` (guest-link token, generated by the server since 006), `data` jsonb = **the whole plan**, plus share/lookup columns (`share_status` draft|published|revoked, `share_expires_at`, `lookup_mode`, `lookup_pin_hash`, `show_tablemates`, `show_layout`). RLS: owner only.
- Plan (`appState.S`, `js/core.js`): `{event:{name,type,date,palette,lang}, guests:{id:{name,group,side,kid,meal,allergies,look}}, waiting:[], rules:[{type:'apart'|…,a,b}], venue:[{type:'dance'|'stage'|'bar',x,y,w,h}], tables:[{id,name,shape,deco,seats:[guestId…],x,y}]}`.
- Saving: `savePlan()` overwrites `data` 1.5 s after the last change (debounced), keeps a draft copy in localStorage, and the last write wins (no concurrency check yet; roadmap R8/P1D).
- Name search (guest page, organiser search) compares names both as typed and as a Latin "skeleton" (`supra_skel` in `007`, `skel()` in `js/core.js` and the mock), so Georgian names typed in Latin letters match. Keep the SQL and the two JS copies identical.
- RSVP (`008`, design in `docs/RSVP_DESIGN.md`): `invites` (one row per household, owner-only RLS, server-made token, answer cleaned by a trigger) and `invite_log`. Guests call only `rsvp_get(token)` / `rsvp_answer(token, answer)`. Answers never go into `events.data`.
- Event details for RSVP live in the plan (`S.event.time`, `venue`, `mapUrl`, `rsvp:{open,deadline,deadlineAt,msg}`) and `savePlan()` also writes them to the event columns via `eventCols()` (Tbilisi time = UTC+4). **Saving needs migration 008 in the database.**
- RSVP answers reach the plan in `js/invites.js` (`invRefresh` → `invApply`, one undoable `commit`): meals into guests, extra guests into Unseated with `S.rsvpExtra[gid]={inv,name}`, then `invites.applied_at` is set so each answer is applied once. `planSVG({rsvp:true})` (on-screen plan only) marks guests who can't come.
- Guests never read `events` directly. They call `public_plan(token)` (layout and drawings only, no names) and `find_seat(token, query, code)` (one name at a time, rate-limited). **Never send meals, allergies, groups, notes, rules or the waiting list to the guest page.** Tests enforce this.

## Rules
- Every user-visible string goes through `t()` and gets **both** `en` and `ka` entries with the same `{placeholders}` (test `every_key_translated_with_same_placeholders`). Write natural Georgian.
- Code is formatted with Prettier 3.3.3 (`.prettierrc.json`: 120 columns, single quotes, quoted keys kept). Before committing JavaScript: `npx prettier@3.3.3 --write js/*.js dash.js i18n.js names.js brand.js config.js tests/e2e/mock-supabase.js`. `assets.js` is never formatted.
- Database changes: new numbered migration file (`007_…sql`), additive (`if not exists`, `create or replace`), with rollback notes and SQL tests in `tests/sql/`. Owner functions must check `owner = auth.uid()`.
- Accessibility is tested: buttons need `type` and an accessible name, panels are tabs with arrow keys, and phone sheets are modal.
- Never touch the live Supabase project from tests or scripts. Use the mock or a separate dev project.

## Tests
- Browser (104 tests, all passing on 2026-11-18): `python3 tests/e2e/run_all.py` (needs `pip install playwright` + `python -m playwright install chromium`). The harness serves the site with Vercel's routes, swaps `supabase.min.js` for `tests/e2e/mock-supabase.js` (state in localStorage: `mockdb`, `mocksess`, `mockcfg`) and loads `tests/e2e/fixture-plan.json` (event `ev1`, guest link `/e/guestcode1`). RSVP tests seed `invites` through `Ctx(..., invites=[...])`; the mock implements `rsvp_get`/`rsvp_answer` like migration 008 (`mockcfg.rsvp = 'net' | 'rate'` simulates failures). Add new tests as `@test` functions in `tests/e2e/test_*.py`.
- Database: `tests/sql/run.sh -h <host> -p <port> -U postgres` against an empty Postgres 15+.
- Run the browser tests after every change. When a migration changes, run the SQL tests too.

## Running locally
No dev server exists yet. To view the app with fake data, reuse `tests/e2e/harness.py` (`serve()` + `Ctx(pw, base, viewport=…)`) from a small Playwright script and take screenshots. Without the harness, a plain static server would use the **live** Supabase from `config.js`.
