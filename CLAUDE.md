# Supra: wedding seating planner

Couples sign in, draw their hall, seat guests (each guest is an illustrated character), print PDFs and place cards, and share a "find my seat" guest page (link + QR). English and Georgian. Goal: turn it into a paid product (couples pay per event, banquet halls/planners pay monthly). See `docs/ROADMAP.md` for the risk register (R1–R12), what is done and **what's next** (section 0 is the current status and backlog).

## Stack
- Plain static site, **no build step, no package.json**. ES2020 in IIFEs, string-template rendering into the DOM and SVG.
- Supabase (Auth + Postgres, RLS, `security definer` functions). Loaded from the CDN: `@supabase/supabase-js@2.45.4` UMD.
- Hosted on Vercel; auto-deploys from `main`. `vercel.json` rewrites `/edit/:id`, `/e/:slug` and `/r/:token` to `app.html`, and `/account` to `/` (`index.html`).

## Files
- `theme.css`: the shared look (design direction A, "a calm table, warm guests", chosen 2026-11-26): named colours (stone, tablecloth, Saperavi black, Saperavi wine as the one accent for the next action, gold only for hairlines and the seat reveal, vine for done), the short role names page CSS uses (`--bg`, `--panel`, `--ink`, `--accent` …), fonts (Noto Serif Display + Noto Serif Georgian for headlines, Noto Sans + Noto Sans Georgian for text) and corner sizes (`--r-control`, `--r-panel`, `--r-pill`). Every page links it before its own styles; pages don't define colours of their own. The event's plan colours (`PALETTES`) are separate. The redesign shipped in nine small steps (2026-11-26): foundations, labels and text, guest page seat reveal, RSVP thank-you, landing, Your events (⋯ menu), planner top bar, selection toolbar (`#selbar`, `renderSelBar`/`placeSelBar` in `js/actions.js`), pricing/account/privacy. Rules to keep: one wine (accent) action per screen; sentence-case labels; gold only for hairlines, bullets and the reveal glow (never body text); peaks (seat reveal, RSVP thanks) animate once and never under reduced motion.
- `privacy.html`: plain-language privacy page (keys `prv*`; `pv*` belongs to the organiser preview). It states exactly what the code stores, sends and keeps (90-day contacts, 30-day trash, 1-day hashed lookup addresses, outside services). **When data handling changes, update this page in the same PR.**
- `pricing.html`: public pricing page (Free / Event pass / Pro, FAQ), text via `data-t` keys `pp*`, own small inline script for language and theme.
- `index.html` + `dash.js`:
  - **Landing page** (signed out): one-column hero ("Every guest, in their seat.", one primary button), the hall in a gold frame, how it works, guests' phone, place cards, sign-in. Text via `data-t` keys `lp*`; pictures `landing/{hall,phone,cards}-{en,ka}.webp` made by `python3 tools/landing_shots.py` from a demo wedding in the real app (re-run it after changing how the hall, guest page or place cards look).
  - **Signed-in header**: language switch, theme switch and an initials button (`#acctbtn`) opening the account menu (Your events, Account and settings, Plans and pricing, Sign out).
  - **"Your events"** (signed-in home): a greeting by time of day, the next wedding large (nearest upcoming date, else last edited) with **one next step** (add guests → seat everyone → publish the guest page → add the date → copy the link; `nextStep()` in `dash.js`), the feast painting `art/feast.webp` in a gold frame above it once that file exists (prompt and conversion in `docs/ART.md`; the frame stays hidden without it), then one card per event (status line, date/countdown/edited, seating bar, seated/tables/free seats/plan, a checklist with a progress ring from the same steps as `nextStep()` (`steps()`), invitation replies by household from `invites` when there are any, Open planner, Copy guest link, ⋯ menu with Open the guest page and Move to trash), the Trash section, and the new-event panel (on demand, or on first run).
  - **Account page** `/account`: password, sign out everywhere, plans, download all data as JSON, delete account via `delete_my_account()` from `012`.
- `app.html` + `js/*.js`: planner (`/edit/<id>`), public guest page (`/e/<token>`) and RSVP page (`/r/<token>`). ES modules: `app.html` loads `js/main.js`, which imports the rest and calls `boot()`. `appState.MODE` is `'edit'`, `'guest'` or `'rsvp'`. `/edit/<id>?panel=event|guests|invites|share` opens the planner on that panel. State several files change lives in `appState` (`js/core.js`), e.g. `appState.S` (the plan), `appState.sel`, `appState.panel`. **Read `js/README.md` before adding files, imports or top-level code.**
- `i18n.js`: `SUPRA_I18N.en` / `.ka` (~990 keys each; test `no_key_is_defined_twice` guards against duplicates). `t(key, vars)` and `tn(key, n)` (plural forms `_one`/`_other`; Georgian nouns stay singular).
- `assets.js` (3 KB) + `img/*.webp`: the drawings (character parts, tables, decorations) as separate files named by content hash, cached for a year (`vercel.json`). `assets.js` holds only sizes, skin colours and the file list; it is generated by `tools/split_assets.py` (never edit by hand). Pages load only what they draw with `loadImages(keys)` in `js/core.js` (planner and guest page: all; RSVP: the household's `lookImages`). Images are kept in memory as data URLs so PNG/PDF exports keep working.
- The room (`hall()` in `js/draw.js`) is drawn from above like the plan: parquet, walls, windows with daylight, trees, entrance. Only guests are drawn from the front. New drawings come from Gemini on a solid green/magenta background; the originals live in `new-art/` (not committed), get cut out to `img/<key>.webp` and registered with `python3 tools/split_assets.py --from-dir`.
- Big plans (R9): `planSVG()` returns `parts` (hall, title, pools, each venue item `v:id`, each table `t:id`, legend); `renderPlan()` replaces only the parts whose markup changed when the list of parts and the viewBox are the same, else rebuilds. Keep each part self-contained (its own defs/clip ids) and keep parts deterministic (no random ids), or every redraw rebuilds the hall. Text fields that change the plan live redraw it 120 ms after typing pauses. Don't write `<html lang>` (use `setDocLang`), the viewBox or the plan size when unchanged: each restyles or relayouts the whole hall. Seats use a roving tabindex (one Tab stop per table, `appState.seatFocus`; arrows, Home and End move between seats). The organiser search also finds tables and zooms in when the view is too small to read. Measure with `tests/e2e/bigplan.py` (`big_event(n)`).
- Planner motion (`renderPlan` in `js/actions.js` + CSS in `app.html`): only in answer to what the organiser does, and off under prefers-reduced-motion.
- `names.js`: guesses man/woman from Georgian/English first names, the family (surname) and grandparents (titles). `smartLook()` in `js/core.js` uses these plus the couple's "Typical guests" shades (`S.event.crowd`) for a new guest's first drawing; relatives look alike. Looks changed by hand carry `look.hand` and are never restyled.
- `art/`: artwork outside the drawing set (the feast painting); see `docs/ART.md`.
- `brand.*`, `brand/`: logo and theme switch. `config.js`: public Supabase URL and publishable key (safe to commit).
- `supabase/*.sql`: migrations, run by hand in order (`schema.sql`, then `002`–`013`) in the Supabase SQL editor. Each file has rollback notes at the top.

## Data model
- One table `public.events`: `owner`, `name`, `type`, `event_date`, `slug` (guest-link token, generated by the server since 006), `data` jsonb = **the whole plan**, plus share/lookup columns (`share_status` draft|published|revoked, `share_expires_at`, `lookup_mode`, `lookup_pin_hash`, `show_tablemates`, `show_layout`). RLS: owner only.
- Plan (`appState.S`, `js/core.js`): `{event:{name,type,date,palette,lang}, guests:{id:{name,group,side,kid,meal,allergies,look}}, waiting:[], rules:[{type:'apart'|…,a,b}], venue:[{type:'dance'|'stage'|'bar',x,y,w,h}], tables:[{id,name,shape,deco,seats:[guestId…],x,y}]}`.
- Saving: `savePlan()` writes `data` 1.5 s after the last change (debounced) and keeps a draft copy in localStorage. Since `010` the server counts plan changes in `events.version` (trigger; publishing, trash and RSVP details don't count) and the planner saves with `.eq('version', ROW.version)`. No row updated = saved elsewhere meanwhile: `js/conflict.js` asks which version to keep (or quietly loads the newer plan when this tab has no unsaved changes, also on returning to the tab). A draft whose base version is old asks the same question on open. Without the column, the last write wins.
- Plans (`011`): free events seat up to 40 guests; an event pass (79 ₾, one event) or Pro (99 ₾/month, every event of the account) removes the limit. `entitlements` rows are written only by `supra_grant_pass` / `supra_grant_pro` (SQL editor or, later, the bank callback; payments will go through a Georgian bank, TBC or Bank of Georgia), never by clients. Events that existed when `011` first ran got a `launch` pass. The planner loads `event_access(event)` into `appState.ACCESS`; `commit()` undoes a step that takes a free plan past the limit and opens the pass panel (`js/access.js`); RSVP answers use `commit(fn, {allowOver: true})` and are never refused. The server refuses publishing and new invitations for a free event above the limit; editing and saving are never blocked. Unknown plan (older database) = no limit. Prices live in `js/access.js`, `dash.js`, `pricing.html` text (`pp*` keys) and the SQL comments; keep them in step. `config.js` `supportEmail` is shown as the way to buy until online payment exists.
- Version history (`013`): `event_versions` keeps earlier plans (owner-readable only, never sent to guests). A trigger keeps the replaced plan at most every 30 minutes; `add_restore_point(event, reason, data)` keeps one before clearing the plan, a "replace" import, choosing the other version in a save conflict, restoring, or on "Save this version now". Latest 60 per event. Restore (`js/history.js`) is a normal undoable `commit(..., {allowOver: true})` that saves with the 010 check; there is no server-side restore.
- Guest import (`js/import.js`, R10): nothing changes before a preview (columns can be remapped, guests already in the plan are matched by `skel(name)` and skipped, updated or added again, rows without names are counted, the free limit is checked). CSV/TXT is read by our own parser (UTF-8 with or without BOM, UTF-16 BOM; comma, semicolon or tab), Excel through SheetJS. The Seat column is used, so Supra's own export imports back in place (Georgian headings and values included; test `georgian_round_trip_with_supras_own_headings`). Tests replace SheetJS with a stub via `ctx.route('**/xlsx.full.min.js', …)`.
- Trash (`009`): `trash_event` / `restore_event` (owner functions) set `deleted_at`; a trashed event's guest page and RSVP links answer "unavailable", share functions refuse it, and the planner won't open it. RLS allows deleting only events already in the trash ("Delete forever" in Your events, after typing the name). `supra_purge_trash()` empties it after 30 days (schedule with pg_cron).
- Name search (guest page, organiser search) compares names both as typed and as a Latin "skeleton" (`supra_skel` in `007`, `skel()` in `js/core.js` and the mock), so Georgian names typed in Latin letters match. Keep the SQL and the two JS copies identical.
- RSVP (`008`, design in `docs/RSVP_DESIGN.md`): `invites` (one row per household, owner-only RLS, server-made token, answer cleaned by a trigger) and `invite_log`. Guests call only `rsvp_get(token)` / `rsvp_answer(token, answer)`. Answers never go into `events.data`.
- Event details for RSVP live in the plan (`S.event.time`, `venue`, `mapUrl`, `rsvp:{open,deadline,deadlineAt,msg}`) and `savePlan()` also writes them to the event columns via `eventCols()` (Tbilisi time = UTC+4). **Saving needs migration 008 in the database.**
- RSVP answers reach the plan in `js/invites.js` (`invRefresh` → `invApply`, one undoable `commit`): meals into guests, extra guests into Unseated with `S.rsvpExtra[gid]={inv,name}`, then `invites.applied_at` is set so each answer is applied once. `planSVG({rsvp:true})` (on-screen plan only) marks guests who can't come.
- Guests never read `events` directly. They call `public_plan(token)` (layout and drawings only, no names) and `find_seat(token, query, code)` (one name at a time, rate-limited). **Never send meals, allergies, groups, notes, rules or the waiting list to the guest page.** Tests enforce this.

## Rules
- Every user-visible string goes through `t()` and gets **both** `en` and `ka` entries with the same `{placeholders}` (test `every_key_translated_with_same_placeholders`). Write natural Georgian.
- Code is formatted with Prettier 3.3.3 (`.prettierrc.json`: 120 columns, single quotes, quoted keys kept). Before committing JavaScript: `npx prettier@3.3.3 --write js/*.js dash.js i18n.js names.js brand.js config.js tests/e2e/mock-supabase.js`. `assets.js` is never formatted.
- Database changes: new numbered migration file (`007_…sql`), additive (`if not exists`, `create or replace`), with rollback notes and SQL tests in `tests/sql/`. Owner functions must check `owner = auth.uid()`.
- Accessibility is tested: buttons need `type` and an accessible name, panels are tabs with arrow keys, and phone sheets are modal.
- Never touch the live Supabase project from tests or scripts. Use the mock or a separate dev project.

## Tests
- Browser (169 tests in 27 files, all passing on 2026-11-26): `python3 tests/e2e/run_all.py` (needs `pip install playwright` + `python -m playwright install chromium`). The harness serves the site with Vercel's routes, swaps `supabase.min.js` for `tests/e2e/mock-supabase.js` (state in localStorage: `mockdb`, `mocksess`, `mockcfg`) and loads `tests/e2e/fixture-plan.json` (event `ev1`, guest link `/e/guestcode1`). RSVP tests seed `invites` through `Ctx(..., invites=[...])`; the mock implements `rsvp_get`/`rsvp_answer` like migration 008 (`mockcfg.rsvp = 'net' | 'rate'` simulates failures). Add new tests as `@test` functions in `tests/e2e/test_*.py`.
- Database: `tests/sql/run.sh -h <host> -p <port> -U postgres` against an empty Postgres 15+ (all passing on 2026-11-24). No local Postgres? `sudo docker run -d --rm --name supra-pg -e POSTGRES_PASSWORD=test -p 5432:5432 postgres:16`, then `PGPASSWORD=test tests/sql/run.sh -h 127.0.0.1 -p 5432 -U postgres` (the fixture is passed as text, so the server needn't see this folder; run.sh waits for a freshly started container).
- Run the browser tests after every change. When a migration changes, run the SQL tests too.

## Working style
- Small sprints: one focused change per PR, then report what's left (the backlog lives in `docs/ROADMAP.md` section 0). Propose how to split anything bigger first.
- Before committing: run the browser tests, format JavaScript with Prettier, and check the change in screenshots (light, dark, phone; Georgian when text changed).

## Running locally
No dev server exists yet. To view the app with fake data, reuse `tests/e2e/harness.py` (`serve()` + `Ctx(pw, base, viewport=…)`) from a small Playwright script and take screenshots. Without the harness, a plain static server would use the **live** Supabase from `config.js`.
